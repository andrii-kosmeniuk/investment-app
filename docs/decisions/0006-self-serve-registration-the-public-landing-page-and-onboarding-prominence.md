# 0006 — Self-serve registration, the public landing page, and onboarding prominence

- **When:** ADR opened before code 2026-09-11 14:18 CEST (T+29:18); decisions below 14:18 → 15:25 CEST (T+29:18 → T+30:25); implementation in the same change
- **Status:** accepted
- **Context:** Until now a customer existed only if `scripts/seed.ts` created them, and the signed-out entry page was a hero with a sign-in form. The brief asks for a customer who can *become* a customer: open an account, be told exactly what stands between them and investing, and go through Persona before any money moves (ADR-0003 fixed the KYC gate and the design world). Three things were open: how an account is created, what the public page says about the product, and how loudly the app insists on unfinished onboarding once someone is signed in.
- **Asked Corgi?** No. Everything here is inside the brief or a UI judgement; the two places we had to pick a policy Corgi might hold differently (email verification, disclosing that an email is taken) are logged in `ASSUMPTIONS.md`.
- **Touches:** `packages/application` (`signUp`, `CustomerRegistry` port, `EmailTakenError`), `packages/database` (`DrizzleCustomerRegistry`), `packages/contracts` (`signUpRequest`), `apps/api` (`POST /v1/auth/sign-up`, public `GET /v1/models`), `apps/web` (`/`, `/sign-up`, shell notice, `public/plates/`).

## Registration: in-house sign-up, no email verification, Persona is the identity check

- **When:** 2026-09-11 14:20 CEST (T+29:20)
- **Decision:** `POST /v1/auth/sign-up` takes display name, email and password, creates the `customers` row (`kyc_status = not_started`, `trading_blocked = true`) and the `customer_credentials` row in one transaction, and returns a session exactly like sign-in does. Email is normalised (trimmed, lower-cased) before the lookup and the insert; the unique constraint on `customers.email` is the last line, mapped to `409 email_taken`. Passwords are at least 10 characters (no composition rules) and hashed with the existing scrypt helper. There is no email verification, no password reset and no rate limit beyond Fastify's defaults.
- **Options:** (a) keep seeding customers by script — cannot demonstrate onboarding from zero; (b) a hosted identity provider (Clerk/Auth0/Neon Auth) — a third-party session model bolted beside the API-minted one from ADR-0003, for a week-one trial; (c) in-house sign-up reusing the ADR-0003 credential and session code — chosen.
- **Why:** The graded property is that a *new* person hits the KYC gate and the funding gate in the right order, not that account creation is hardened. Reusing the sign-in machinery keeps one session model. Persona already is the identity check, so verifying an email address adds a second, weaker one before the real one; skipping it is a deliberate week-one cut, logged.
- **Consequences:** A registered but unverified customer can look at every page and can start Persona; funding, model choice and orders stay refused by the existing gates (`KycRequiredError`, `TradingBlockedError`). Disclosing "email already exists" at sign-up leaks account existence; acceptable for a sandbox, logged as an assumption. `CustomerRegistry` is a separate port from `CustomerDirectory` so the read side stays read-only.

## The public catalogue

- **When:** 2026-09-11 14:24 CEST (T+29:24)
- **Decision:** `GET /v1/models` is public (no session) and returns the same `ModelResponse[]` the signed-in `/models` route returns: names, risk levels, cash buffers and target weights from configuration. Nothing customer-specific is exposed.
- **Why:** The landing page shows the four models with their real weights rather than marketing copy; the weights are product configuration, not customer data, and the page must never drift from what the API enforces. An unreachable API leaves the plate with an honest "temporarily unavailable" line instead of hard-coded numbers.

## The landing page: a field guide, pre-dithered plates, in-house motion

- **When:** 2026-09-11 14:30 CEST (T+29:30)
- **Decision:** `/` (signed out) is one scrollable page: sticky header (wordmark, section anchors, "Create an account" text link, "Sign in" pill; under 56rem a corner button opening a dropdown with the same anchors and both actions), the ADR-0003 hero with the character-field fern, four product facts, then four numbered **plates** — a dithered monochrome nature figure beside a factual caption: I the five onboarding steps in order, II the four models with allocation bars, III a restatement shown as "as published → as corrected" with the reason, IV the provider sandboxes named as such — a serif closing statement with the two actions, and a footer with the disclaimer. Copy states only what the API enforces; no outcomes, no testimonials, no prices. Plate artwork ships as pre-processed PNG pairs in `apps/web/public/plates/` (ordered Bayer 8×8 dither to ink on white at 600×800, doubled with nearest-neighbour so each cell is 2×2 device pixels, composited with `mix-blend-mode: multiply` so white becomes paper). Motion is CSS only: the plate rule draws in eight steps and the caption rises on first view (IntersectionObserver), the figure "breathes" by cross-fading a second frame whose dither matrix is shifted, the menu button morphs to a close mark; all static under `prefers-reduced-motion`.
- **Options:** Structure: three compositions were dealt from the design tooling (field guide / prose with living proof / statement front page); the user locked the field guide. Artwork: (a) Higgsfield video or image generation — the account's trial only permits use through Higgsfield's MCP server, which is not configured in this workspace, so every CLI generation call was refused; (b) monochrome sources from the editor's image tool, dithered locally — chosen; (c) CSS-only halftone imitation — refused by the brief. Dither at (a) full 2× resolution — reads as grey mush on 1× screens; (b) display resolution then nearest-neighbour ×2 — chosen.
- **Why:** The brief's art direction (ADR-0003: paper, ink, one orange, serif only on the entrance, dithered nature scenes as the only other artwork family) is more distinctive than any stock fintech layout, and a numbered field guide is the one structure where numbering is justified by sequence. Pre-processing the dither keeps the page cheap (≈ 25–70 KB per frame) and deterministic; runtime dithering would cost a canvas per plate for no visible gain. Every shipping raster carries its generation prompt and processing in its PNG `tEXt` chunk (`impeccable embed-prompt --scan apps/web/public/plates` → 0 missing).
- **Consequences:** The landing page is dynamic (it redirects a signed-in visitor to `/overview` and reads the catalogue), so it renders on the server per request; that is fine at this scale. Higgsfield-generated artwork is a cut, logged. The first-viewport header carries one text link and one secondary pill; the single orange primary action sits in the hero (one primary per decision area).

## Onboarding prominence: one shell-wide notice, derived from the rail

- **When:** 2026-09-11 14:40 CEST (T+29:40)
- **Decision:** While any onboarding step is `current` or `blocked`, the signed-in shell renders an accent-tinted band under the top bar on every page except `/onboarding`: the next step as the heading, a status pill that tells the truth about who acts ("Action needed" only when the customer can act; "Verification pending" while Persona holds the inquiry; "Verification declined" in the negative tone), one sentence on what is blocked, the position in the rail ("Step 2 of 5") and a single button. The side/bottom navigation marks "Onboarding" with an orange dot and a visually-hidden "(action needed)". The overview's own KYC alert and "Next step" section are removed; its empty-state button uses the *same* derived action so the two never disagree.
- **Options:** (a) keep the inline alert on the overview only — invisible from Portfolio/Transfers, where the gate actually bites; (b) a modal or forced redirect to onboarding — breaks the brief's "you can look around after the first step"; (c) shell-wide band + nav marker — chosen.
- **Why:** The gate is enforced server-side per action; the UI's job is to say so before the customer hits it, on every page, in one voice. Deriving the band from the server's `OnboardingResponse` (`onboardingNotice`) means the shell never invents a state the API does not hold.
- **Consequences:** The band uses `--accent-soft` (the only tinted surface the world allows) and a `StatusPill`; no label sits above the heading. Once the rail is complete the band and the dot disappear with no further code.
