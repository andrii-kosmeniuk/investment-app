## Operator identity: shared token + declared operator, enforced twice

- **When:** 2026-09-11 10:37 CEST (T+25:37)
- **Decision:** Every `/v1/ops/*` request carries the operator token (ADR-0004) **and** an `X-Operator-Id` header naming a human row in `actors`. The API resolves the actor on each request and refuses agents and unknown ids. Decisions are attributed to that actor; the maker ≠ checker rule is enforced in the domain (`assertValidDecision`) *and* by the database trigger from migration 0002, so a bypassed API still cannot self-approve. The web console asks the operator to pick who they are at sign-in (list from `GET /v1/ops/operators`) and keeps both in the `corgi_ops` cookie.
- **Options:** (a) per-operator credentials (passwords/SSO) — right for production, a day of work that proves nothing about the ledger; (b) the shared token only, with no actor — cannot express maker-checker at all; (c) shared token + declared actor — chosen.
- **Why:** The graded property is that the *system* refuses a self-approval and records who decided, not that the login is hardened. Declaring the actor keeps the attribution trail (`approval_decisions.decided_by_actor_id`) real while the credential stays week-two.
- **Consequences:** Logged as an assumption. Two human operators (Sam Chen, Maya Brooks) and one `system` actor are seeded; the demo shows Sam's request being refused when Sam tries to approve it. A stolen operator token can *claim* to be any operator — same blast radius as today, revoked by rotating one secret.

## Approvals: one queue, one decision use-case, executors per kind

- **When:** 2026-09-11 10:40 CEST (T+25:40)
- **Decision:** `decideApproval` loads the request, validates the decision (pending, human, maker ≠ checker), records the decision row, sets the request status, and — only for `approved` — runs the executor for the request's `kind` in the same unit of work. Executors are small functions keyed by kind: `withdrawal` posts the `withdrawal` ledger entry (settled cash → Plaid sweep) and files the transfer record; `order` submits the stored leg through `placeOrder`; `rebalance` submits the stored legs (sells first, then buys that fit available-to-trade; the rest are reported as `deferred`); `recon_adjustment` posts the adjusting entry and marks the break `resolved` with `resolution_entry_id`. Rejection records the reason and touches nothing else. The request `payload` is the *complete* instruction (customer, legs, amounts, break id); the checker approves what they see, not what is recomputed later.
- **Options:** (a) approve = flip a status and let a job pick it up — a second place to reason about; (b) approve = execute inline — chosen; (c) recompute the effect at approval time — the checker would be approving a moving target.
- **Why:** "Approved" must mean "done or failed loudly", and the audit row must match the effect. Freezing the instruction in the payload is what makes the queue reviewable.
- **Consequences:** Every write that moves money or securities out of a customer's control (withdrawal, sell-to-cover, rebalance, adjusting entry) has exactly one entry point. A customer's own buy stays on the ADR-0003 confirmation path; a buy at/above `ORDER_CONFIRMATION_THRESHOLD_CENTS` without confirmation still lands in this queue as `order`. Withdrawals book the ledger leg; the Plaid *credit* transfer that pays the bank is not initiated (cut — see CUT_LIST), so the row is labelled "payout not sent" in the console.

## Agent writes become proposals with frozen legs

- **When:** 2026-09-11 10:43 CEST (T+25:43)
- **Decision:** MCP `propose_rebalance` now runs the same `proposeRebalanceForCustomer` use-case the console uses: value the portfolio at the latest closes, compute drift legs with the domain `proposeRebalance` (buffer, minimum trade, Hamilton cent), and file a `rebalance` approval whose payload holds the legs and the prices used. `request_withdrawal` checks the amount against *withdrawable* cash (settled − unsettled buys) before filing. Both are `requested_by_actor_type = 'agent'` and are tagged in the queue. `get_reconciliation_breaks` reads the real breaks with aging.
- **Options:** (a) keep the inserts in `services.ts` — two code paths for one thing; (b) share the use-case — chosen.
- **Why:** The agent must propose exactly what a human would, so the checker cannot tell the source apart except by the tag. `docs/AGENT_BOUNDARIES.md` stays the list of what the agent is never handed.
- **Consequences:** An agent proposal for an unfunded or unassigned customer is rejected at proposal time with a clear error rather than filing an empty request.

## Reconciliation: simulator file, zero tolerance, aging from first sighting

- **When:** 2026-09-11 10:47 CEST (T+25:47)
- **Decision:**
  - *File.* A custodian file is one CSV per business date with three sections (`positions`, `cash`, `transactions`), quantities in micro-units / cents, as of the prior close. We have no real custodian, so a **simulator** builds it from the ledger as at `endOfBusinessDay(date)` and stores the content (sha256, `custodian_files.content`) — labelled `source = simulator`. The live-fire console can inject a **tamper** (add/remove units or cents, drop a transaction) when it generates the file; the worker generates an untampered file at 06:00 ET if none arrived.
  - *Run.* `runReconciliation(date)` uses the latest file on or before the date (the "No file for Sep 12 — using Sep 11" edge state), compares positions per (customer, symbol) and settled cash per customer with **zero** tolerance, and transactions by ledger entry id (`missing_transaction` = in ledger, not in file; `unexpected_transaction` = in file, not in ledger). Price breaks (50 bps) are defined but not produced — the file carries no prices this week. When the broker is configured, Alpaca positions are fetched and shown as a **third column** (`broker_value`) but do not create breaks on their own.
  - *Breaks.* A break is identified by (customer, category, key). A run inserts new breaks with `first_run_id`, refreshes `last_seen_run_id` on those it sees again, and leaves ones it no longer sees untouched — a break closes only by a human: **explain** (note, status `explained`) or **adjust** (files a `recon_adjustment` approval; approval posts the entry and sets `resolved`). Aging = today − the *business date of the first run that saw it*; buckets 0–1d, 2–3d, 4+d.
- **Options:** Tolerance: (a) zero — chosen, logged earlier as an assumption; (b) a cent — hides real breaks in a fractional-share book. Auto-close: (a) resolve breaks that vanish — silent; (b) keep until a human acts — chosen. Storage: (a) object storage — another provider; (b) text column — chosen, files are kilobytes.
- **Why:** Reconciliation is worth points only if a tampered unit shows up as a break the same morning with 0-day aging and a three-column diff, and if closing it leaves a trail. Zero tolerance on integers is the honest default for a book that stores exact micro-units.
- **Consequences:** Migration 0005 adds `custodian_files.content`, `recon_breaks.broker_value`, `resolution_note`, `resolved_by_actor_id`, `resolved_at`. The recon screen shows runs, breaks with buckets, and the three columns; the empty state reports the counts matched.

## Settlement: T+1 from recorded fills, weekends only

- **When:** 2026-09-11 10:52 CEST (T+25:52)
- **Decision:** `applyFill` records a `settlements` row per execution (`pending`, `trade_date`, `contractual_settlement_date = addBusinessDays(tradeDate, 1)`, `amount_cents`). The 00:05 ET job `settleDueTrades` posts `settleBuy` / `settleSell` for every pending row whose date has arrived, idempotent on `settle:{fillExternalId}`, and marks it `settled` with the entry id. The holiday set is empty this week (NYSE calendar is on the cut list), so settlement skips weekends only. Sell fills are booked with a new `sellFill` pattern (position → trading units; proceeds to `unsettled:sells`) and consume FIFO lots into `lot_consumptions`.
- **Options:** (a) settle at fill time — hides the T+1 gap the brief asks to see; (b) settlement rows written by the fill handler and settled by a job — chosen.
- **Why:** The gap between "bought" and "settled" is the thing the portfolio page must show (unsettled buys pill), and a job that reads its own table is easier to reason about than one that re-derives due fills from the ledger.
- **Consequences:** Migration 0005 adds `settlements.amount_cents`. A fill replayed after settlement is a no-op at every layer (ledger key, settlement unique index, lot consumption keyed by the sell entry).

## Bounce after invest: firm covers, trading stops, humans decide the recovery

- **When:** 2026-09-11 10:57 CEST (T+25:57) · assumption, question emailed 10:24
- **Decision:** On `transfer.returned` the existing entry (settled cash → `receivable:bounce_recovery`) is posted. If the customer's settled cash is then negative — the money was already invested — `handleDepositReturn` additionally sets `trading_blocked = true`, and files an `order` approval `{ intent: "sell_to_cover", customerId, amountCents = shortfall, returnCode }` requested by the `system` actor. Approving it submits a sell for the shortfall through `placeOrder` with `firmInitiatedSell = true` — the only way past `trading_blocked`, and only for sells. The recovery is closed by an explicit operator action, `POST /v1/ops/customers/:id/release-trading-block`: once settled cash is ≥ 0 again it posts `bounce_recovered` (receivable ← plaid sweep, idempotent per customer and day) and lifts the block; it refuses while cash is still negative. The customer sees an amber "Trading is paused" banner on the portfolio; nothing is sold without a human.
- **Options:** (a) auto-sell immediately — an agent-free but human-free money movement; (b) do nothing until ops notice — the receivable sits unowned; (c) block + queue — chosen.
- **Why:** A return code like R01 is a fact about the bank, not about the customer's intent; liquidating without a human is exactly what `AGENT_BOUNDARIES.md` forbids the agent, and the same logic applies to a cron.
- **Consequences:** If Corgi answers differently (e.g. never sell, collect from the customer), a superseding ADR changes the executor; the ledger accounts already separate the receivable from cash so no restatement is needed.

## Events: replay proves "twice is one"

- **When:** 2026-09-11 11:02 CEST (T+26:02) · narrowed 2026-09-11 11:20 CEST (T+26:20) while implementing
- **Decision:** `GET /v1/ops/events` lists inbound events with their attempts; `POST /v1/ops/events/:id/replay` re-submits the stored event through the same `inbox.receive` path the webhooks use and returns its verdict — `duplicate` for anything already seen. It does **not** re-run the handler: the inbox is the idempotency boundary the providers hit, and a second one (the ledger's key) is already proven by the use-case tests that replay fills and transfers. Running handlers from an HTTP route would also race the worker's lease loop.
- **Why:** The live-fire row "replay a fill → duplicate" needs a button that goes through the production path; anything else would be theatre. The first draft of this section promised both results from one call; that would have meant a second execution path for handlers in the API, which is more surface than the proof needs.
